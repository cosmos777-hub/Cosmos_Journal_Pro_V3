# Purpose

Le module **Journal** constitue désormais le **Reference Module** officiel de Cosmos Journal Pro V3.

Il représente le niveau de qualité, de cohérence et de finition attendu pour tous les futurs modules du projet.

Aucun nouveau module ne doit être considéré comme terminé s'il n'atteint pas un niveau de qualité comparable.

---

# Why the Journal?

Le Journal est le premier module à avoir bénéficié d'un cycle complet de conception, développement, polishing, audit et validation.

Il a servi de laboratoire pour construire :

- la philosophie produit ;
- la philosophie UX ;
- le Design System ;
- les règles de composition visuelle ;
- les conventions de développement ;
- les standards de documentation.

Tous les futurs modules devront s'appuyer sur ces fondations.

## Technical Architecture

Le Journal respecte la structure officielle du projet.

### Core

Responsable uniquement de la logique métier.

Aucun accès direct au DOM.

Exemples :

- state.js
- storage.js
- calculations.js
- mediaStorage.js

---

### UI

Responsable uniquement de l'interface.

Aucune logique métier.

Communication avec Core uniquement via les API prévues.

---

### Storage

Deux niveaux de stockage sont désormais officiels.

#### LocalStorage

Données métier :

- trades
- paramètres
- préférences
- statistiques

#### IndexedDB

Données lourdes :

- captures HTF
- captures LTF
- captures Résultat

Chaque technologie possède une responsabilité clairement définie.

# Official Architectural Patterns

Les patterns suivants deviennent des standards du projet.

## Single Source of Truth

Chaque information possède un seul propriétaire.

Aucune duplication de logique.

---

## Single Scroll Owner

Une seule zone de scroll par espace fonctionnel.

Jamais de double scrollbar.

---

## Double Viewport

Viewport fixe.

Contenu réel.

Scroll unique.

Ce pattern devient la référence pour tous les futurs panneaux complexes.

---

## Component Isolation

Chaque composant possède une responsabilité unique.

Les composants restent indépendants.

---

## Progressive Enhancement

Les nouvelles fonctionnalités enrichissent le produit.

Elles ne cassent jamais les workflows existants.

Un module n'est jamais considéré terminé après compilation.

Il doit être audité.

Les audits doivent couvrir :

- comportement fonctionnel ;
- architecture ;
- performances ;
- cohérence visuelle ;
- mémoire ;
- régressions.

MEDIA-001 constitue le modèle d'audit à reproduire.

# Lessons Learned

Le développement du Journal a permis d'établir plusieurs principes durables.

Une interface compacte peut rester très confortable.

Le workflow est plus important que la richesse visuelle.

Le polishing doit être continu.

Les audits finaux sont indispensables.

La documentation doit évoluer au même rythme que le code.
