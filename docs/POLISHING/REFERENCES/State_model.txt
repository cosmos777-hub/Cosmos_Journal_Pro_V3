# STATE_MODEL.md

**Cosmos Journal Pro V3 — Design System**
Version : 1.0
Statut : Officiel (créé lors d'UI-004)

---

## 1. Rôle de ce document

Ce document est la référence officielle des **états** du Design System de
Cosmos Journal Pro. Il évite qu'un futur ticket redéfinisse un comportement
déjà tranché, ou applique un état à un composant qui n'en a pas besoin.

**Principe fondateur (UI-004)** : tous les états ne sont pas de même nature.
Un état de composant, un état de notification et un état de flux applicatif
ne se comportent pas de la même façon et ne s'appliquent pas aux mêmes
éléments. Les confondre est la source la plus fréquente d'incohérence dans
un Design System. Ce document les classe donc en **trois catégories**
étanches.

---

## 2. Les trois catégories d'états

### 🟦 Component States
Un état intrinsèque à un composant réutilisable, indépendant de toute action
en cours. Le composant sait afficher cet état par lui-même, sans dépendre
d'un flux applicatif.
→ **Empty**, **Disabled**.

### 🟨 Feedback States
Une teinte sémantique appliquée à un message pour indiquer le résultat d'une
action déjà terminée (succès, échec, information neutre). Ne décrit jamais
une action *en cours* — seulement son issue.
→ **Success**, **Error**, **Neutral**. Portés par : Toast, Import Feedback.

### 🟥 Workflow States
Un état qui décrit le déroulement d'un processus applicatif dans le temps
(attente, confirmation) plutôt qu'un composant ou un message. Peut être
partiellement ou totalement hors du Design System visuel.
→ **Loading** (Reserved), **Confirmation** (hors Design System).

**Règle de non-mélange** : un Component State ne doit jamais être utilisé
pour communiquer le résultat d'une action (c'est le rôle d'un Feedback
State), et un Feedback State ne doit jamais être utilisé pour représenter
l'état permanent d'un composant (c'est le rôle d'un Component State).

---

## 3. Component States

### Empty 🟢 Stable
**Définition** : état d'un conteneur de contenu qui n'a rien à afficher.
**Implémentation** : `.empty-state` (CSS) + `emptyState(title, message)` (JS, voir `COMPONENT_CATALOG.md` §3.3).
**Composants concernés** : listes de contenu — historique Journal, liste
filtrée Analytics, vue Insights (`#insights-empty-state`, variante dédiée
car conditionnée par le seuil de 30 trades, Document 05 §7).
**Composants exclus** : boutons, champs de formulaire, notifications — Empty
n'a de sens que pour un conteneur qui *pourrait* contenir une liste
d'éléments.
**Règle d'usage** : toujours accompagné d'un message qui oriente l'utilisateur
vers une action (Document 03 : *"Aucun trade enregistré → Ajoutez votre
premier trade"*), jamais un simple "0" ou "Vide".

### Disabled 🟢 Stable
**Définition** : état d'un contrôle d'action rendu volontairement
non-interactif.
**Implémentation** : `:disabled` sur `.button`, `.nav-button`, `.icon-button`
(introduit lors d'UI-002) — opacité réduite, curseur `not-allowed`,
interactions désactivées via `pointer-events: none`.
**Composants concernés** : famille de boutons d'action.
**Composants exclus** : `.chip` et `.star-button` (sélecteurs de valeur, pas
des actions déclenchables — voir `COMPONENT_CATALOG.md` §3.4) ; les listes
de contenu (Empty s'en charge).
**Statut d'usage actuel** : **posé en fondation, non déclenché**. Aucun
bouton de l'application n'est désactivé aujourd'hui — c'est volontaire (voir
`DECISIONS_LOG.md`, D-008 : le Design System peut poser des fondations en
avance du besoin fonctionnel).

## 4. Feedback States

### Le principe de teinte (introduit lors d'UI-004)

Les Feedback States réutilisent le **même vocabulaire de teinte** que le
reste du Design System (`positive` / `negative` / `neutral`), déjà en usage
pour `badge()` et les valeurs de KPI (`utils.tone()`). Ce n'est pas un
nouveau système de couleurs — c'est l'extension d'un système existant à deux
nouveaux porteurs : le toast et le texte de statut inline.

| Teinte | Couleur | Signification |
|---|---|---|
| `positive` | `var(--success)` | L'action demandée par l'utilisateur a réussi |
| `negative` | `var(--danger)` | L'action a échoué, ou l'utilisateur doit corriger quelque chose avant de continuer |
| `neutral` *(par défaut)* | couleur de texte standard | Message informatif, ni succès ni échec (ex. migration automatique, fichier chargé en attente de confirmation) |

### Toast 🟢 Stable
**Rôle** : notification flottante et temporaire (Document 03 : *"jamais de
popup, des toasts élégants"*).
**API** : `ui.toast(message, tone = "neutral")` — le paramètre `tone` est
optionnel, tout appel existant `ui.toast("message")` reste valide et neutre
(rétrocompatibilité garantie).
**Rendu** : le style reste toujours discret quelle que soit la teinte — un
liseré et une couleur de texte teintés, **jamais un fond plein** (Document 03 :
*"jamais flashy"*).
**Exemples classés** :
- `positive` : "Trade enregistré.", "Compte créé.", "Export copié.", "Import réussi..."
- `negative` : "Sélectionnez un actif et une stratégie.", "Ce trade n'existe plus.", "Gardez au moins une option."
- `neutral` : "Données V2 migrées vers les fondations V3." (information automatique, pas une réponse à un clic)

### Import Feedback 🟢 Stable
**Rôle** : statut inline (non flottant) affiché sous le champ d'import JSON —
persiste tant que l'utilisateur reste sur la modale, contrairement au toast
qui disparaît après 3 secondes.
**API** : `ui.setFeedback(element, message, tone = "neutral")` — nouveau
helper générique (`components.js`), réutilisable par tout futur texte de
statut inline du même type.
**Rendu** : combine `.muted` (taille de police) et la classe de teinte
(couleur) — les deux coexistent sans conflit car ils ne portent pas la même
propriété CSS.
**Exemples classés** :
- `positive` : "Import réussi : 3 compte(s), 42 trade(s)."
- `negative` : "JSON invalide...", "Ce fichier ne ressemble pas à une sauvegarde Cosmos valide.", "La sauvegarde n'a pas pu être validée.", "Impossible de lire ce fichier."
- `neutral` : "Fichier chargé : export.json" (information d'étape, pas encore un résultat), réinitialisation du champ à l'ouverture de la modale

### Exception documentée — Mise en évidence de champ en erreur ⚪ Hors périmètre
Le Document 03 prévoit qu'un champ invalide soit visuellement mis en
évidence lors de la validation d'un formulaire. **Ce comportement n'existe
pas aujourd'hui** — la seule validation actuelle (`actions.saveTrade`) se
limite à un toast générique (`negative`), sans cibler de champ précis.
**Décision (UI-004, R5)** : volontairement laissé hors périmètre. Ajouter ce
comportement toucherait à la logique de validation métier (`main.js`), pas
seulement à l'habillage visuel — ce n'est pas un sujet de Design System pur.
**Suivi** : à traiter dans un futur ticket dédié à la validation de
formulaire (backlog produit, hors Sprint 2).

## 5. Workflow States

### Loading 🔵 Reserved (Conceptual)
**Définition** : état d'attente pendant qu'une opération asynchrone est en
cours.
**Pourquoi il n'est pas implémenté** : toutes les opérations actuelles de
Cosmos Journal Pro sont **synchrones** — écriture `localStorage`, calculs en
mémoire, changement de vue. Aucune latence perceptible n'existe aujourd'hui
dans l'application. Créer un composant de chargement sans aucun déclencheur
réel serait de la sur-ingénierie, contraire à la devise du projet
(*Rapidité · Efficacité · Qualité*).
**Note historique** : le Document 03 décrit un bouton passant à *"✓
Enregistrement..."* pendant la sauvegarde d'un trade. Ce comportement n'a
jamais été implémenté dans le code — l'opération étant instantanée, il n'y a
rien à afficher pendant son exécution. Ce n'est pas une régression d'UI-004,
c'est un écart préexistant entre l'aspiration du Document 03 et la réalité
technique (l'opération ne dure pas assez longtemps pour qu'un état
intermédiaire soit perceptible).
**Conditions d'implémentation future** : ce concept devra être activé le
jour où une opération réellement asynchrone apparaîtra dans l'application
(ex. synchronisation cloud — Document 07, Roadmap V4). Tant que ce jour n'est
pas arrivé, **aucun CSS, aucune classe, aucun spinner ne doit être créé** en
prévision — à la différence de `.icon-button` ou de l'état `:disabled`
(UI-002), Loading n'a aujourd'hui aucun terrain d'application concret, même
non déclenché.

### Confirmation ⚪ Hors Design System
**Définition** : état de flux où l'utilisateur doit valider ou annuler une
action destructive avant qu'elle ne s'exécute (suppression d'un trade,
réinitialisation de l'historique, import écrasant les données).
**Implémentation actuelle** : `confirm()` natif du navigateur.
**Décision (UI-004, R6)** : conservé tel quel. Remplacer `confirm()` par une
modale stylée Cosmos serait l'introduction d'une **fonctionnalité nouvelle**
(gestion d'état de modale personnalisée, focus trap, etc.), pas la
formalisation d'un état existant — hors de l'objectif du Sprint 2 (Document
04 §13 impose déjà la confirmation obligatoire pour toute suppression ; seul
le *rendu visuel* de cette confirmation resterait à traiter, dans un futur
ticket UX si cela devient prioritaire).

## 6. Tableau de synthèse

| État | Catégorie | Statut | Composants concernés | Composants exclus |
|---|---|---|---|---|
| Empty | Component | 🟢 Stable | Listes de contenu (Journal, Analytics, Insights) | Boutons, champs, notifications |
| Disabled | Component | 🟢 Stable | `.button`, `.nav-button`, `.icon-button` | `.chip`, `.star-button` |
| Success / Error / Neutral | Feedback | 🟢 Stable | Toast, Import Feedback | Composants de contenu (ce n'est pas leur rôle) |
| Loading | Workflow | 🔵 Reserved (Conceptual) | *(aucun aujourd'hui)* | Tous, tant qu'aucune opération asynchrone n'existe |
| Confirmation | Workflow | ⚪ Hors Design System | *(navigateur natif)* | — |

## 7. Règle pour l'ajout d'un nouvel état

Avant d'ajouter un état au Design System, se poser ces questions dans
l'ordre :
1. **Est-ce un état permanent d'un composant, ou le résultat d'une action ?**
   → Permanent = Component State. Résultat = Feedback State.
2. **Décrit-il un composant précis, ou le déroulement d'un processus dans le
   temps ?** → Processus = Workflow State.
3. **Existe-t-il un besoin technique réel aujourd'hui, ou seulement une
   possibilité théorique ?** → Sans besoin réel, documenter comme *Reserved*
   plutôt que d'implémenter (voir Loading ci-dessus) — sauf si l'extension
   est triviale sur un système déjà en place (voir `.icon-button`/`Disabled`,
   `DECISIONS_LOG.md` D-008).
4. **Peut-il réutiliser un vocabulaire de teinte ou une classe existante ?**
   → Toujours préférer l'extension d'un système existant (`positive`/
   `negative`/`neutral`) à l'invention d'un nouveau nom.
